# 악보 메이커

음악 파일이나 YouTube 영상 링크를 가져와 SAM Audio로 여섯 악기를 차례로 분리하고, 악기별 음원을 악보로 변환하는 웹 작업실입니다. React + TypeScript 프런트엔드와 Python 3.11 FastAPI API로 구성했습니다.

## 지금 사용할 수 있는 기능

- 파일 선택·드래그 앤 드롭·업로드 전 미리듣기. MP3, WAV, FLAC, M4A, AAC, OGG, OPUS, MP4, MOV, WEBM, MKV, AIFF 지원. FFmpeg로 동영상의 오디오 트랙도 추출합니다.
- YouTube 개별 영상 URL 입력, yt-dlp 다운로드. 기본 200MB·10분 제한. 로그인·쿠키·라이브·재생목록·보호된 영상은 지원하지 않습니다.
- SAM Audio 순차 분리, 작업 진행률, 중단, 브라우저 새로고침 후 작업 복원. 긴 음악은 20초 구간과 2초 겹침으로 처리합니다.
- 악기별 WAV, 마지막 잔여 음원, 파형, 솔로·음소거·볼륨·재생 위치, 원본 비교.
- 악기별 채보 → 16분음표 단위 정리 → MusicXML·MIDI. 보컬·베이스는 pYIN 단선율, 기타·피아노·신디는 악기별 Basic Pitch 설정을 사용합니다. 드럼은 실험적 다중 대역 온셋 검출 또는 별도 환경의 드럼 모델을 연결합니다.
- 실제 MusicXML 악보 렌더링, 음표 크기·보표 간격·마디 번호, 브라우저 인쇄/PDF 저장, 전체 ZIP 다운로드.
- 출력 스타일 선택: 드럼·베이스·기타 기본값인 합주용(넓은 간격), 기본, 큰 악보(2마디 중심). A4 기준 배치를 화면에 맞춰 축소해 모바일에서도 음악의 줄바꿈을 유지합니다.
- 악보 직접 수정: 음표 추가·삭제, 음정/드럼 종류·위치·길이·세기 교정, 마디 복사, 실행 취소/다시 실행, 제목·BPM·구간 표시·마디 아래 메모. 저장하면 악보·MIDI·MusicXML·ZIP에 함께 반영됩니다.
- 베이스·기타 TAB: **TAB 위 + 오선 아래가 새 악보 기본값**. 순서/단독 표기 선택, 줄·프렛 직접 입력, 튜닝·카포, 자동 운지, 뮤트·정수 반음 벤딩 표기. 악센트·스타카토·테누토 표기도 지원합니다.
- 피아노·신디: 높은음자리/낮은음자리 대보표 기본값, 단일 보표 전환, 자동 음역 분리와 음표별 오른손/왼손 지정. 기존 저장본은 사용자 선택 전까지 기존 단일 보표를 유지합니다.
- 여러 음표/마디 범위 일괄 음정·위치·길이·세기 변경/삭제, 한 번의 실행 취소. 임의 마디의 새 줄/새 페이지 시작을 저장·출력합니다.
- MusicXML/XML/MXL 파트 선택 가져오기: 음원 없이 새 프로젝트를 열거나 기존 편집 초안에 가져와 스타일을 변경합니다. 2/4·3/4·4/4·6/8·9/8·12/8과 마디별 변박을 보존합니다. 16분음표 격자에 맞지 않는 리듬과 미지원 표기는 거절합니다. PDF/이미지 인식은 아직 없습니다.
- 채보/빈 악보의 박자 선택, 편집기의 마디별 박자 변경·삭제, 점음표 입력. 박자 변경 시 음표·가사의 시간 위치를 유지하고, 가사 입력·범위 선택·복사·재생·출력도 실제 마디 길이를 사용합니다.
- 가사·보컬 진입: CPU 로컬 Whisper로 단어별 시간 초안 생성, 원본을 들으며 텍스트·시간 수정, 전체 파트 적용. 직접 입력·일반 LRC 가져오기·파트별 독립 수정도 지원하며 악보·인쇄·MusicXML에 반영합니다.
- CPU BPM·박 위치 분석, 반속/배속 제안, 채보 시작 오프셋. ‘분리 없이 원본만 분석’으로 SAM/GPU 없이 실제 파일 분석과 빈 악보 직접 입력을 사용할 수 있습니다. 악기별 자동 채보에는 실제 분리 음원이 필요합니다.
- 편집한 음표의 간단한 합성음 미리듣기, 마디 범위·느린 재생·반복·재생 마디 강조. 드럼의 8분음표는 기본 네 개(두 박)씩 연결하고 1박/2박 빔 묶음을 선택할 수 있습니다.
- 이 브라우저의 최근 20개 프로젝트, 모바일 화면, 키보드 조작, 오류 및 엔진 연결 상태 안내.
- 직접 합성한 원본 샘플 음원과 실제 WAV·MIDI·MusicXML 파일로 작업실 체험. **샘플은 SAM Audio 분리 결과가 아닙니다.**

## 서버 실행 (권장)

nvm, uv, Git, FFmpeg가 설치된 Linux NVIDIA 서버에서 다음 한 줄로 실행합니다.

```sh
./start.sh --host 192.168.100.15 --port 8000
```

접속 주소는 http://192.168.100.15:8000 입니다. 다른 서버에서는 해당 서버 주소를 지정하세요. 인자를 생략하면 127.0.0.1:8000에 바인딩합니다.

스크립트가 nvm으로 Node 22를 선택/설치하고, uv로 Python 3.11과 `.venv`를 준비합니다. SAM Audio, CUDA PyTorch, Basic Pitch, Whisper를 포함한 고정 의존성을 설치한 뒤 프런트엔드를 빌드하고 웹앱과 API를 함께 실행합니다. 설치된 Python 패키지와 모델 캐시는 다음 실행에서도 재사용하며 프런트엔드는 매번 새로 빌드합니다. `./start.sh --setup-only`는 패키지 설치와 빌드까지만 수행합니다.

**기본 실행은 모든 엔진이 준비되어야 성공합니다.** API가 요청을 받기 전에 FFmpeg, 저장소 쓰기 권한, GPU 연산, TorchCodec, SAM Audio 모델, Basic Pitch ONNX 모델, Whisper 모델을 확인·초기화합니다. 첫 실행 때 모델을 다운로드하며, 다운로드/권한/초기화 실패는 단계와 원인을 터미널에 표시하고 서버 시작을 중단합니다. 업로드 후 발생하는 오류도 처리 단계·원인·서버 로그에서 찾을 작업 번호를 표시합니다.

모델 접근 승인은 자동화할 수 없습니다. [SAM Audio 모델](https://huggingface.co/facebook/sam-audio-base)의 접근 승인을 받은 계정으로 인증하거나 `.env`에 `HF_TOKEN`을 설정하세요. 초기화 중 추가 모델의 접근 승인이 요구되면 로그에 표시된 모델에도 권한이 필요합니다. 토큰은 Git이나 프런트엔드에 넣지 않습니다. nvm/uv, NVIDIA 드라이버, OS 패키지는 사전 설치 대상입니다. Ubuntu의 미디어 패키지: `sudo apt-get install git ffmpeg libsndfile1`.

서버 잠금 파일은 Python 3.11/Linux NVIDIA용이며 PyTorch 2.8 / CUDA 12.8 / TorchCodec 0.7 조합을 사용합니다. CUDA 12.8을 지원하는 드라이버가 필요합니다. [TorchCodec 호환표](https://github.com/meta-pytorch/torchcodec)에 맞춰 함께 갱신하세요. Basic Pitch와 SAM의 protobuf 제약 충돌을 해결한 upstream audiotools와 resampy의 `pkg_resources`에 필요한 setuptools 버전도 고정했습니다. 잠금 파일 갱신 명령:

```sh
GIT_LFS_SKIP_SMUDGE=1 uv pip compile backend/requirements-server.in --python-version 3.11 --torch-backend cu128 -o backend/requirements-server.lock
```

## 샘플·개발 실행 (엔진 준비 검사 명시적 생략)

Node 22 이상, Python 3.11, FFmpeg가 필요합니다. macOS는 `brew install ffmpeg`, Ubuntu는 `sudo apt-get install ffmpeg libsndfile1`로 설치할 수 있습니다.

```sh
source "$HOME/.nvm/nvm.sh"
nvm use
npm ci
uv venv --python 3.11
uv pip install -r backend/requirements-dev.txt
```

두 터미널에서 각각 실행합니다.

```sh
AKBO_ALLOW_DEGRADED=1 uv run uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

```sh
npm run dev
```

웹앱: http://127.0.0.1:5173 · API 문서: http://127.0.0.1:8000/docs

개발용 `AKBO_ALLOW_DEGRADED=1`을 명시하면 ML 패키지 없이 샘플 작업실을 실행할 수 있습니다. 실제 분리는 사용할 수 없는 상태로 표시되며, 샘플이나 원본 음원을 분리된 음원으로 위장하지 않습니다. 일반 실행에서는 이 옵션을 설정하지 마세요.

## GPU 없는 원본 분석과 가사 인식

홈에서 `분리 없이 원본만 분석`을 체크하고 파일/영상 링크를 가져오면 FFmpeg로 원본을 준비합니다. SAM 추론은 호출하지 않으며 악기별 WAV도 만들지 않습니다. 이 모드에서는 원본 BPM·박 분석, 가사 인식, 악기별 빈 악보 생성과 수동 편집을 사용할 수 있습니다. 파일·YouTube 제한과 사용 권한 안내는 일반 업로드와 같습니다.

가사 자동 인식용 선택 패키지는 다음과 같이 설치합니다.

```sh
uv pip install -r backend/requirements-asr.txt
```

[faster-whisper](https://github.com/SYSTRAN/faster-whisper)의 다국어 `base` 모델을 CPU INT8로 실행합니다. `.env`의 `LYRICS_MODEL`로 모델을 선택하며, 첫 실행 때 모델을 `.data/models/whisper/`에 다운로드합니다. 이후 인식은 로컬에서 수행하고 업로드한 음원은 ASR 서비스로 전송하지 않습니다. `/api/health`의 `lyrics.available`은 패키지 존재 여부이지 모델 다운로드나 노래 인식 품질의 보증이 아닙니다.

‘가사 타임라인’에서 원본/분리 보컬과 언어를 선택합니다. 인식 결과는 즉시 악보를 덮어쓰지 않고 검토할 초안으로 보관합니다. 각 항목의 시작·끝 시간(원본 기준 초)과 단어를 교정하고 `초안 저장` → `전체 파트에 적용`을 선택합니다. 기존 악보의 가사만 대체하며 음표·운지·메모·최초 생성본은 보존합니다. 적용한 공통 가이드는 이후 새로 만드는/재채보하는 악보에도 배치됩니다. 여러 탭의 후보/악보 revision 충돌은 차단합니다. 현재 악보 편집기는 먼저 저장하고 닫아야 전체 적용할 수 있습니다.

노래·강한 반주·코러스·무보컬 구간에서는 Whisper가 가사를 누락하거나 없는 단어를 만들 수 있습니다. 단어 시간은 ASR 추정이며 음악적인 음절 정렬/멜리스마 분석은 아닙니다. 분리 보컬이 대체로 유리하지만 정확도는 실제 곡에서 확인해야 합니다. 실제 노랫말이 없는 합성 샘플은 자동 가사 인식에서 제외합니다. 가사 초안도 브라우저 임시 보관과 미저장 이탈 경고를 제공합니다.

템포 분석은 librosa로 원본의 처음 최대 180초를 확인합니다. 첫 검출 박은 **마디 첫 박이라는 보장이 없으며**, 표시한 박 간격 규칙성도 정확도/신뢰도 점수가 아닙니다. 반속/배속을 들어보고 채보 BPM과 ‘악보 첫 박의 원본 위치’를 직접 확인하세요. 설정은 다음 채보/빈 악보 생성에만 적용되고 기존 악보를 자동으로 바꾸지 않습니다. 오프셋 이전 음표·가사는 제외하므로 인트로도 필요하면 0초를 유지하세요.

## 실제 SAM Audio 엔진 연결

권장 서버 실행 스크립트는 SAM Audio와 호환 CUDA 패키지를 자동 설치합니다. 환경만 수동으로 준비하려면 Python 3.11 `.venv`에서 다음을 실행하세요. [SAM Audio 공식 설치 안내](https://github.com/facebookresearch/sam-audio)도 참고하세요.

```sh
GIT_LFS_SKIP_SMUDGE=1 uv pip install --torch-backend cu128 -r backend/requirements-server.lock
```

[사용할 Hugging Face 모델](https://huggingface.co/facebook/sam-audio-base)에 접근을 요청해 승인받고, 해당 서버에서 `hf auth login`으로 인증하거나 `.env`에 `HF_TOKEN`을 설정하세요. `.env.example`의 나머지 설정도 사용할 수 있습니다. 토큰은 백엔드에서만 읽고 프런트엔드나 Git에 포함하지 않습니다.

```dotenv
SAM_MODEL=facebook/sam-audio-base
SAM_DEVICE=cuda
SAM_MIN_FREE_GB=12
SAM_MAX_GPU_UTILIZATION=10
SAM_CHUNK_SECONDS=20
MAX_AUDIO_SECONDS=600
MAX_UPLOAD_MB=200
```

모델 경로를 `SAM_MODEL`로 지정하면 로컬 체크포인트도 사용할 수 있습니다. 일반 서버 실행은 모델 다운로드와 초기화가 끝나야 요청을 받습니다. GPU 메모리가 부족하면 구간 길이를 줄이거나 작은 SAM 모델을 선택하세요. 시작 검사는 긴 실제 음원의 메모리 사용량이나 분리 품질까지 보증하지 않습니다. 모델·패키지·GPU·인증 상태는 `/api/health`와 화면의 연결 상태에서도 확인할 수 있습니다.

`SAM_DEVICE=cuda` 또는 `auto`는 각 분리 작업 실행 직전에 `nvidia-smi`로 GPU 상태를 조회합니다. 기본적으로 사용률 10% 이하이고 여유 메모리 12 GiB 이상인 GPU 중 가장 여유 메모리가 많은 장치를 선택합니다. 위 환경변수로 기준을 조절할 수 있으며, 큰 모델에는 더 높은 메모리 기준이 필요합니다. `CUDA_VISIBLE_DEVICES`로 제한하거나 순서를 바꿔도 UUID로 장치를 매칭합니다. `SAM_DEVICE=cuda:1`처럼 번호를 지정하면 해당 CUDA 장치에 고정합니다.

한 작업의 여섯 악기는 같은 GPU에서 처리하고, 다음 작업에서 다시 선택합니다. 조건을 만족하는 GPU가 없으면 작업에 재시도 안내를 표시하며 자동 대기하지 않습니다. 시작 검사에서도 GPU를 선택하므로 모두 사용 중이면 서버 시작이 중단됩니다. 선택한 GPU는 서버 로그와 `/api/health`의 `engine.selected_device`에서 확인할 수 있습니다(유휴 시 `null`). 사용량 조회는 다른 사용자의 GPU 예약을 보장하지 않으므로, 선택 후 다른 프로세스가 메모리를 할당하면 작업이 실패할 수 있습니다.

이 앱은 텍스트 프롬프트·후보 1개·구간 예측 비활성 설정으로 분리하므로 ImageBind/CLAP/Judge 재평가 모델과 구간 예측 모델을 로드하지 않습니다. 시작 시 4초 무음으로 실제 SAM 분리를 수행해 처리기·추론·파형 반환까지 확인합니다. 이는 음악 분리 품질 평가가 아니며, 여러 GPU에 모델을 자동 분산하지 않습니다.

시작 검사와 각 분리 작업이 끝나면 SAM 모델을 CPU RAM으로 옮기고 CUDA 할당 캐시를 반환합니다. 실패·취소 때도 같은 정리를 수행합니다. 다음 분리 요청에서는 CPU에 보관한 모델을 GPU로 다시 옮기므로 모델 다운로드는 반복하지 않지만 전송 시간이 추가됩니다. 여섯 악기 분리 도중에는 모델을 유지하며 단일 작업 큐에서 작업 종료 후에만 해제합니다. 유휴 상태에서도 CUDA 실행 컨텍스트·라이브러리의 소량 메모리는 남을 수 있습니다. `/api/health`의 `engine.gpu_resident`는 현재 SAM 모델의 GPU 상주 여부이며, `ready`는 시작 검사를 통과했는지 표시합니다.

순차 분리의 핵심은 다음과 같습니다. `extract` 결과는 한 번만 계산합니다. 48kHz 모노 부동소수점 WAV로 중간 결과를 저장하여 단계별 클리핑을 피합니다.

```python
residual = audio.copy()
for inst in ["vocal", "bass", "drums", "synthesizer", "guitar", "piano"]:
    target = extract(residual, inst)
    outputs[inst] = target
    residual = residual - target
# sum(outputs.values()) + residual ≈ audio
```

이 구조는 앞 단계의 분리 오류가 다음 단계에 영향을 줄 수 있습니다. 모든 곡에 여섯 악기가 실제로 존재하는 것은 아니며, 비슷한 음색의 악기를 모델이 혼동할 수 있습니다. 해당 악기 소리가 매우 작으면 화면에 안내합니다.

## 채보와 악보 스타일

SAM Audio는 소리를 분리하고, [Spotify Basic Pitch](https://github.com/spotify/basic-pitch)는 기타·피아노·신디 등 다성 음원의 음정·시작·종료를 추정합니다. 보컬·베이스는 기본적으로 CPU pYIN의 단선율 추적을 사용하며 ‘화음 포함’으로 전환할 수 있습니다. 드럼은 음정 채보 대신 타격 시각과 종류를 추정합니다. 악기별 경로와 한계는 아래 개선 현황을 참고하세요.

현재 채보는 사용자가 확인한 고정 BPM, 선택한 박자표, 16분음표 격자를 사용합니다. **자동 완성 악보가 아니라 확인·수정이 필요한 초안**입니다. BPM·박 위치와 가사 초안은 CPU 분석으로 제안합니다. 박자표/변박/마디 첫 박 자동 검출, 구간별 템포 지도, 조성 추정, 실제 연주에 따른 건반의 손/독립 성부 인식은 아직 없습니다. 건반은 음역 기반 두 보표 분리와 수동 손 지정을 지원합니다. MusicXML은 외부 악보 편집기에서도 수정할 수 있습니다.

### 박자표 · 변박

2/4·3/4·4/4·6/8·9/8·12/8을 지원합니다. 새 채보/빈 악보는 박자를 먼저 선택하고, 편집기의 `박자표 · 변박`에서 마디를 선택해 그 마디부터 바꿉니다. 뒤에 이미 지정한 박자 변경은 기존 **마디 번호**에서 계속 적용됩니다. 음표의 시작·길이와 가사 시간은 그대로 두고 마디선만 다시 나눕니다. 마지막 마디 부족분은 쉼표로 채우며 음원 길이는 바꾸지 않습니다.

구간 메모와 수동 줄/페이지 시작은 기존 마디 첫 위치를 포함하는 새 마디로 옮깁니다. 한 마디에 모인 메모는 합치고, 글자 제한을 넘으면 변경을 거절합니다. 새 첫 마디로 옮겨진 줄/페이지 시작은 첫 페이지 자체에 포함됩니다. 적용 전 안내·실행 취소·미리보기·저장 충돌 검사를 유지하므로 인쇄 전 위치를 확인하세요. 긴 마디의 음표가 짧은 마디에 들어맞지 않으면 마디 붙여넣기를 거절하고 대상 음표를 지우지 않습니다.

BPM은 모든 박자에서 **4분음표 기준**입니다. 예를 들어 6/8에서 점4분음표 60은 이 앱의 BPM 90과 같습니다. MusicXML의 [sound tempo](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/sound/)와 MIDI에도 같은 기준을 사용합니다. 고정 메트로놈의 점음표 템포는 가져올 때 4분음표 BPM으로 환산합니다. 6/8·9/8·12/8의 빔은 8분음표 세 개씩, 두 번째 빔은 8분음표 단위로 나눕니다. MusicXML/MIDI에 마디별 박자표를 기록하며 기존 저장본은 4/4로 읽고 음표·revision·채보 원본 파일을 바꾸지 않습니다. 잇단음표·못갖춘마디·5/8·7/8·자유 박자는 아직 지원하지 않습니다.

## 악보 편집과 출력 스타일

악보가 생성되면 `악보 직접 수정`을 눌러 마디별로 교정할 수 있습니다. 드럼은 킥·스네어·하이햇·오픈 하이햇·크래시·라이드·하이/미드/플로어 탐 입력을 지원합니다. 기본 CPU 분류기는 킥·스네어·하이햇만 추정하며, 동시 타격 후보를 독립적으로 검출합니다. 나머지 종류는 직접 입력하거나 별도의 전용 모델 연결이 필요합니다. 심벌/스네어는 위쪽 기둥, 킥은 아래쪽 기둥으로 분리하고 음표 연결을 MusicXML에 명시합니다.

새 자동 드럼 악보는 짧은 소리의 감쇠 시간을 그대로 음표 길이로 쓰지 않고, 같은 성부의 다음 타격·마디 끝·최대 한 박 묶음 길이까지로 정리합니다. 연속 8비트/16비트의 하이햇이 짧은 음표와 불필요한 쉼표로 갈라지는 것을 줄입니다. 타격 시각·종류·세기는 유지하며 MIDI의 노트 종료 시각은 정리된 길이를 따릅니다. 사용자가 저장하거나 MusicXML로 가져온 길이는 이 처리로 다시 바꾸지 않습니다.

- 격자의 한 칸은 16분음표입니다. `●`/TAB 숫자는 음표 시작, `—`는 앞 음표의 이어짐이며 쉼표가 아닙니다. 빈칸은 음표 추가, 시작/이어짐 칸은 선택, 시작 음표 더블클릭/삭제 버튼은 삭제입니다. 이어짐을 넣으려면 음표를 선택하고 길이(칸)나 `1칸 늘리기`를 사용합니다. 같은 음정/같은 TAB 줄의 겹침은 허용하지 않습니다.
- 음표 연결선(빔)은 1박 또는 2박씩 묶습니다. 드럼 기본값은 2박이라 8분음표 네 개씩 연결합니다. 16분음표는 첫 번째 선을 2박으로, 두 번째 선을 1박으로 나누며 쉼표/긴 음표에서 끊습니다. 설정은 음표 길이·MIDI를 변경하지 않습니다.
- 기존 악보의 연결선은 자동으로 덮어쓰지 않습니다. 편집기에서 `음표 연결선(빔)` → `2박씩`을 선택하고 저장하면 새 묶음을 반영합니다. 드럼은 하이햇만 있는 마디도 5선 보표로 유지하고 가사가 있는 쉼표 마디를 다중 쉼표로 축약하지 않습니다.
- 마디 번호 입력/이전·다음 버튼으로 이동합니다. 미리보기의 마디를 클릭해도 이동합니다. 격자에서는 방향키로 이동할 수 있습니다. 편집기 안에서 `Ctrl/Cmd+S`로 저장, `Ctrl/Cmd+Z`로 실행 취소합니다.
- 구간 표시(A/B/Intro 등)와 마디 아래 메모는 직접 입력합니다. 메모는 가사의 정밀한 음절 배치가 아닌 마디 단위 힌트이며 인쇄와 MusicXML에 반영됩니다. 참고 악보의 로고·워터마크·QR·곡 내용은 제품에 복사하지 않았습니다.
- 스타일은 고정하지 않습니다. 합주용/기본/큰 악보 중 선택하고 2/4마디 배치를 저장합니다. 작은 화면에서는 `가독성 확대`로 악보를 좌우로 읽을 수 있습니다. 이 보기 확대는 인쇄를 바꾸지 않습니다. 화면 크기 설정은 보기·인쇄에만 적용되고, 저장한 출력 스타일은 MusicXML에도 기록됩니다. 다른 편집기의 레이아웃 해석은 다를 수 있습니다. 복잡한 마디는 겹침을 피하기 위해 목표 마디 수보다 적게 배치될 수 있습니다.
- 미리보기는 서버의 기존 파일을 덮어쓰지 않습니다. `저장하고 반영` 이후 편집기를 닫아 MusicXML·MIDI·ZIP을 받거나 인쇄/PDF로 저장합니다. BPM 편집은 악보/MIDI 템포만 바꾸며 원본 음원 속도는 유지합니다.
- `악보 듣기`는 저장 전 음표도 간단한 합성음으로 재생합니다. 현재 마디부터 마지막 마디를 선택하고 0.5/0.75/1/1.25배속과 반복을 사용할 수 있습니다. 재생 마디를 강조하고 정지/편집/마디 이동/화면 종료 때 합성음도 중지합니다. 실제 악기 사운드폰트가 아닙니다. 편집기의 원본/분리 음원 플레이어도 최초 채보 BPM·시작 오프셋과 저장한 변박으로 현재 마디를 강조하며, 두 플레이어는 서로 중지해 겹쳐 재생하지 않습니다. 구간별 템포 변화 기반의 정밀 동기화와 음표 단위 커서는 후속 기능입니다.
- 음표 목록 Shift+클릭이나 일괄 수정의 마디 범위 선택으로 여러 음표를 이동·조절합니다. 충돌/범위 초과 시 전체 변경을 거절하고, 음정 이동은 운지 배정만 초기화합니다. 드럼은 반음 이동을 사용할 수 없습니다. 새 줄/페이지는 현재 마디에서 시작하며 2마디 이후에 지정합니다.
- 자동 채보 원본을 따로 보관하여 `채보 원본`으로 돌아갈 수 있습니다. 복원도 저장 전에는 서버 파일을 바꾸지 않으며 실행 취소할 수 있습니다. 재채보는 수정본을 대체하므로 UI 확인과 API의 `overwrite_edits` 동의가 필요합니다.
- 브라우저에 저장 전 편집본을 임시 보관하고 다시 열 때 복원을 제안합니다. 최신 서버 버전과 같은 경우만 복원하며, 브라우저 저장소를 지우면 임시본도 사라집니다. `JSON 보관`은 수동 백업 용도이며 JSON 가져오기는 아직 지원하지 않습니다. 여러 탭의 저장 충돌은 revision 검사로 차단합니다.

### TAB 우선 편집

베이스는 4/5/6현, 기타는 6/7현 튜닝 프리셋과 Drop D를 지원합니다. 1번 줄이 가장 높은 줄이며 프렛 0은 개방현입니다. 새 악보는 **TAB 위, 오선 아래**로 함께 표시하고 기존 저장본은 이전 순서를 보존합니다. `위쪽 보표`에서 변경·저장할 수 있습니다. 오선은 일반적인 옥타브 이조 표기이고 MIDI와 운지는 실제 소리의 음정(콘서트 피치)을 유지합니다.

카포 0~12는 MusicXML의 [capo 표기 규칙](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/capo/)에 따라 개방현 음정을 올립니다. 프렛은 카포 기준 상대 위치이고 실제 음정은 `튜닝 + 카포 + 프렛`입니다. 카포 변경은 음표의 소리를 유지하고 운지만 다시 제안합니다. 연주 표시에서 X 음표(뮤트)와 정수 반음 벤딩을 지정할 수 있습니다. 합성 미리듣기는 짧은 뮤트·단순 벤딩을 근사하지만 실제 주법 음색은 아니며 MIDI는 기본 음정·길이·세기를 유지합니다.

빈칸을 누르면 입력 프렛·길이로 추가하고, 숫자를 누르면 속성 편집에서 선택합니다. 더블클릭이나 삭제 버튼으로 지울 수 있습니다. 줄을 바꾸면 음정을 유지한 프렛을 계산하고, 프렛을 바꾸면 음정도 함께 바뀝니다. 한 줄에서 겹치는 음표는 저장할 수 없습니다.

자동 운지는 줄 수·음역·동시 발음·대략적인 손 이동을 고려하는 제안입니다. 실제 연주자의 운지를 알아내는 모델이 아니며 해머링·풀링·슬라이드·프리벤드/릴리스는 아직 없습니다. 범위를 벗어난 음은 임의로 옥타브를 바꾸지 않습니다. 미배정 음은 오선에 남지만 TAB에서 제외되므로 **TAB만 출력하기 전에는 미배정 수를 확인**하세요. 튜닝 변경/운지 초기화 후 저장하면 다시 배정합니다. 기존 프로젝트는 편집기를 열면 TAB 데이터가 추가되며 저장 이후 일반 보기/내보내기에도 반영됩니다.

### 가사와 합주 진입 위치

현재 합성 샘플에는 실제 노랫말이 없어 자동 인식하지 않습니다. 실제 음원은 프로젝트의 ‘가사 타임라인’에서 CPU 인식·검토·전체 적용하고, 편집기의 `가사 · 보컬 진입`에서는 파트별 음절·단어·짧은 문장·진입 힌트를 원하는 마디와 시작 칸에 배치합니다. 쉼표 구간도 지원하며 결합 악보는 아래쪽 보표 아래, 단독 악보는 해당 보표 아래에 표시합니다. MusicXML의 실제 `<lyric>` 정보로 내보냅니다. 긴 가사는 2마디/큰 악보 출력과 짧은 항목으로 나누는 것이 좋습니다.

일반 LRC의 `[00:12.34]가사`, 반복 시간 태그, `[offset:250]` 밀리초 오프셋을 지원합니다. 최대 512KB, 한 항목 80자이며 곡 밖 항목은 제외하고 동일 칸 충돌은 거절합니다. 시간은 원본 기준으로 받아 **원래 채보 BPM과 악보 시작 오프셋**을 적용해 16분음표 칸에 반올림합니다. 공통 가이드 적용에서는 같은 칸에 모인 단어를 합치고 80자를 초과하면 거절합니다. 이후 BPM 편집은 가사/음표 칸이나 원본 음원 재생 위치를 옮기지 않습니다. 확장 LRC의 음절 시간 태그와 SRT는 아직 지원하지 않습니다. 정확한 합주 위치는 음원과 직접 비교해야 합니다.

저장 후 `저장한 가사를 다른 악보에 복사`하면 다른 생성된 악보의 가사만 대체하며 음표·TAB·메모를 유지합니다. 대상 악보의 수정본 revision은 변경되어 이전 탭이 덮어쓰지 못하고 자동 채보 원본도 보존됩니다. 다른 채보 BPM인 경우 원래 시간 기준으로 변환하며 충돌/범위 초과 시 복사 전체를 거절합니다. 복사 후 각 악보의 가사를 독립적으로 수정할 수 있고 자동 동기화되지는 않습니다.

이 편집기는 마디 편집기이며 완성형 악보 제작 프로그램은 아닙니다. 오선 음표 직접 드래그, 셋잇단음표·반복기호·다이내믹·코드 기호는 아직 지원하지 않습니다.

### MusicXML 가져오기

홈 아래 `기존 악보 가져와서 스타일 바꾸기`에서 2MB 이하 MusicXML/XML/MXL의 파트와 악기를 선택합니다. 음원 없이 새 악보 프로젝트를 생성하며 분리 음원을 위조하지 않습니다. 처음 가져온 XML은 다운로드와 ZIP에 별도로 포함합니다. 여러 파트 파일은 선택한 한 파트씩 가져옵니다.

편집기에서도 파트를 가져올 수 있습니다. 음표·가사·메모·마디 수를 편집 초안에서 대체하지만 원본 음원/재생 기준·출력 스타일·최초 생성본은 유지합니다. 실행 취소할 수 있고 저장 전에는 서버 파일을 바꾸지 않습니다. 편집기에서 나중에 가져오는 파일의 원본은 서버에 추가 보관하지 않으므로 직접 보관하세요.

현재 4분음표 기준 고정 BPM 40~240, 지원 박자의 완전한 마디·변박, 16분음표 격자에 정확히 표현 가능한 최대 600마디를 지원합니다. 화음·성부 이동·타이·한 절 가사·줄/프렛·튜닝·카포·기본 연주 표시를 읽고, 오선/TAB 중복 음표와 타이를 합칩니다. 피아노·신디는 두 보표의 배정을 보존하며, 음역이 교차해도 위/아래 보표 지정을 유지합니다. 원본 보이스 분리·음자리표 변경·이명동음/조표·레이아웃은 재배치됩니다. 잇단음표·못갖춘마디·반복·다이내믹·코드/장식음·여러 절/멜리스마 등은 현재 보존할 수 없어 가져오기를 거절합니다. 지원되지 않는 리듬을 임의로 반올림하지 않습니다.

업로드/압축 해제 크기·파일 수·XML 요소 수·숫자 파싱을 제한하고 내부 DTD/엔티티와 ZIP 경로 탈출을 거절합니다. 외부 DTD를 내려받거나 MXL의 파일을 디스크에 풀지 않습니다. PDF/이미지 OMR은 이 기능과 다르며 아직 구현하지 않았습니다.

## 전 악기 채보 개선 · 현재 단계

**음표 인식, 시간 정렬, 악보 조판은 별개의 문제입니다.** 두 보표로 보기 좋게 출력해도 잘못 검출된 음정은 저절로 고쳐지지 않습니다. 재채보 전 BPM·박자·첫 박 위치를 확인하고, 분리 음원을 들어 해당 악기가 충분히 남아 있는지도 확인하세요. 새 엔진/방식 정보는 악보 JSON과 파트 메타데이터에 저장합니다. 기존 프로젝트의 음표나 원본을 자동으로 덮어쓰지 않습니다.

| 악기 | 현재 채보 경로 | 기본 표기와 검토 대상 |
| --- | --- | --- |
| 보컬 | CPU pYIN 기본음 추적, 비브라토 안정화, 무음·재발음 구분 | 단일 멜로디 보표 + 공통 가사. 코러스/겹친 보컬의 주선율 선택은 미해결 |
| 베이스 | 저음용 긴 분석 창의 pYIN, 필요 시 ‘화음 포함’ Basic Pitch | TAB 위 + 오선 아래. 5현 저음/튜닝·카포·실제 운지 확인 |
| 기타 | 음역·최소 음 길이·온셋 기준을 적용한 다성 Basic Pitch | TAB 위 + 오선 아래. 화음을 유지하되 배음/잔향·줄 배정 검토 |

| 드럼 | 독립 대역 온셋 또는 선택 설치한 ADT_STR | 타악기 5선·성부·빔. 기본 검출기는 3종만 추정하며 스네어/심벌 분류 한계가 큼 |

보컬·베이스의 ‘화음 포함’은 다시 채보할 때 적용합니다. 전체 악기 재채보는 각 악기의 기본 방식을 사용합니다. 건반의 `악보 직접 수정 → 건반 악보 형식`에서는 음정·길이·MIDI를 유지한 채 표기만 변경합니다. 경계음(기본 C4) 미만은 왼손으로 자동 배정하며, 음표별 지정이 우선합니다. 보컬·드럼 등 단일 보표의 가사는 그 아래, TAB/대보표의 가사는 아래쪽 보표 밑에 표시합니다. 가사는 기존 가사 타임라인에서 별도로 검토·적용해야 하며 멜로디 채보가 노랫말을 생성하지는 않습니다.

### 선택 사항: 별도 환경의 드럼 전용 모델

`backend/drum_worker.py`와 `scripts/transcribe-drums.py`는 [ADT_STR 공식 추론 API](https://github.com/pier-maker92/ADT_STR)의 로컬 모델을 격리된 프로세스로 호출합니다. **2026-10-06 macOS arm64 CPU에서 실제 체크포인트 추론, 무음 검사, 공개 녹음의 수동 정답 비교까지 실행했습니다.** SAM 환경이나 회사 배포 서버는 변경하지 않았습니다. 모델 연결 성공과 실제 곡의 악보 정확도는 다릅니다. 아래 비교처럼 모든 곡에서 경량 검출보다 좋은 것은 아닙니다.

별도 Python 3.11 환경의 재현 절차(다운로드는 운영자가 명시적으로 실행):

```sh
git clone https://github.com/pier-maker92/ADT_STR.git .data/drum-runtime/ADT_STR
git -C .data/drum-runtime/ADT_STR checkout --detach 77dbef225e7029478ebfb916f20c7a00274f0f12
uv venv --python 3.11 .data/drum-runtime/.venv
uv pip install --python .data/drum-runtime/.venv/bin/python -r requirements-drum.txt
HF_HOME=.data/drum-runtime/hf-cache .data/drum-runtime/.venv/bin/python scripts/prepare-drum-model.py
```

`prepare-drum-model.py`는 `Pierfrancesco/adt-str`의 `a33c5c6b191a4ca1e0f6dc22140947485eb36ce8` / `setting-tau-0.8`만 다운로드하고 SHA-256 매니페스트를 남깁니다. 가중치는 약 290MB입니다. `AKBO_DRUM_MODEL_DIR`은 그 안의 **`setting-tau-0.8` 폴더**를 가리켜야 합니다. 나머지 `AKBO_DRUM_*` 경로는 `.env.example`을 참고하세요. 요청 처리 중 패키지/체크포인트를 설치하지 않으며, HF 오프라인 모드에서 매니페스트의 체크섬과 소스 커밋을 검증합니다. TorchCodec 없이 soundfile→tensor API로 입력합니다. `/api/health`의 `drum_engine.paths_ready`는 파일 설정 검사일 뿐 실제 추론 성공 보증은 아닙니다.

**라이선스:** 공식 소스는 CC-BY-SA-4.0, 확인한 [HF 모델 카드](https://huggingface.co/Pierfrancesco/adt-str)는 별도 가중치 라이선스를 명시하지 않습니다. 로컬 검증과 별개로, 가중치 배포·공개/상업 서비스 적용 전 사용 조건을 확인해야 합니다. 가중치·외부 소스·평가 음원은 Git에 포함하지 않습니다.

사이트의 드럼 파트에서 `자동 / 전용 AI / 교차검증 AI (실험) / 보강 AI (실험) / 경량 검출`과 `분리된 드럼 / 원본 전체 음원`을 선택한 뒤 다시 채보할 수 있습니다. `자동`은 **운영자가 워커를 설정했을 때만** 전용 AI를 사용합니다. 잘못된 워커 설정/실행 실패를 경량 검출로 숨기지 않습니다. `분리 없이 원본만 분석`으로 올린 드럼 녹음도 `원본 전체 음원`을 선택하면 GPU/SAM 없이 채보할 수 있으며 다른 파트를 분리 완료로 표시하지 않습니다. 전체 믹스를 바로 채보하면 다른 악기를 드럼으로 오인할 수 있습니다.

모델의 26종 **전용 번호 체계는 GM과 다릅니다.** 예를 들어 모델 44/46/48은 오픈 하이햇/크래시/라이드이므로 GM 46/49/51로 먼저 변환합니다. 이후 11종 편집기 표기(기존 9종 + 사이드스틱/페달 하이햇)로 정리합니다. 페달 하이햇은 킥과 아래 성부, 사이드스틱은 스네어 위치의 x음표로 표시합니다. 세부 탐/심벌 변종 통합과 미지원 타악기 수는 별도 기록합니다. 미지원 타격을 스네어로 강제 변환하지 않습니다. 새 자동 채보에서 타격의 표기 길이는 다음 타격/박 경계까지만 유지해 불필요한 다음 박 연결 타이를 줄입니다. 수동 입력·가져온 악보의 길이는 바꾸지 않습니다.

`AI 원본 타격·검토 데이터`에서 `drums.raw.mid`와 `drums.transcription.json`을 받을 수 있습니다. 원본 MIDI는 박자 격자 적용 전 GM 타격과 악보에 표시하지 못한 타악기를 유지합니다. JSON은 원본 타격, 통합/미지원 내역, 모델/패키지 버전, 시간 구간별 원시 토큰과 불완전 출력 경고를 포함합니다. 토큰은 시작 시각·악기·세기 묶음으로 엄격하게 읽어 잘못된 토큰 뒤의 음정을 이전 시각에 붙이지 않습니다. 경량 엔진으로 재채보하면 이전 AI 원본을 현재 결과로 다운로드/ZIP에 포함하지 않습니다.

실행 제한은 1회 분석 10분, 3회 교차검증 30분이며 실행 중 취소는 추론 반환 뒤 반영됩니다. 기존 1회 CPU는 12초 녹음당 약 6~27초(프로세스 시작 포함, 1차 측정)였으며 긴 곡의 소요 시간은 보장하지 않습니다. CUDA 지정 시 해당 별도 환경의 메모리를 확인해야 하고 SAM의 GPU 선택 정책은 이 프로세스에 적용되지 않습니다.

### 실제 드럼 녹음 비교 · 1차 기준선 · 2026-10-06

[MDB Drums](https://github.com/CarlSouthall/MDBDrums)의 사람이 연주하고 수동 표시한 정답을 사용했습니다(C. Southall, C. Wu, A. Lerch, J. Hockman, ISMIR 2017). 고정된 5곡의 첫 12초씩, 정답 타격 총 313개입니다. **작은 진단용 부분집합이며 학습 데이터와 독립임을 보증한 홀드아웃 평가나 전체 곡 정확도가 아닙니다.** 모델 출력으로 정답을 만들거나 이 정답에 맞춰 임계값을 조정하지 않았습니다.

| --- | ---: | ---: | ---: |
| 80sRock | 0.7636 | 0.5867 | 0.9855 |
| Rock | 0.4773 | 0.7556 | 0.3273 |
| FunkJazz | 0.6154 | 0.6711 | 0.7586 |

| 합산(micro) F1 | **0.5364** | **0.7196** | **0.7133** |

음정/종류가 같은 타격의 시작 시각 ±50ms를 일대일 매칭한 F1입니다. 11종 킷의 GM 변종은 정규화하되 비킷 타악기 오인식도 분모에 포함합니다. 하이햇 개방/닫힘·페달과 사이드스틱은 서로 다른 종류로 평가합니다. 사람이 표시한 **시작 시각만** 정답이며, 길이·빔·박자 정렬/악보 표현 점수가 아닙니다.

같은 구간의 **원본 전체 믹스** 합산 F1은 기존 0.3777 / 경량 0.4362 / ADT 0.3716이었습니다. 이 실험의 드럼 단독 WAV는 데이터셋 제공 녹음으로 **SAM 분리 결과가 아닙니다.** 따라서 회사 서버의 분리 품질 개선을 검증한 수치로 해석하면 안 됩니다. ADT가 잘한 구간도 있으나 Rock의 하이햇 누락, Reggae의 카우벨 오인식, 일부 청크의 토큰 출력 중단이 남아 있습니다. 전용 AI를 일괄적인 품질 개선으로 홍보하지 않습니다.

BPM 추천값 적용은 시작 위치와 분리했으며, 저장한 시작 위치는 새로고침/파트 변경 후에도 불러옵니다(기존 파일은 읽기 전용 보완). 이는 사용자 흐름 검사이며 BPM/다운비트 정답 평가가 아닙니다. 서버 자동 테스트 219개와 프런트엔드 25개, 별도 실제 ADT 추론 테스트 2개가 통과했습니다. 일반 테스트에서 GPU 1개와 명시 실행용 ADT 2개는 건너뜁니다.

### 드럼 보강 AI · 2차 실험 · 2026-10-06

`보강 AI · 하이햇 보완 (실험)`은 사용자가 명시적으로 선택하는 비교용 엔진입니다. **자동/기존 전용 AI의 기본값은 바꾸지 않았습니다.** 다음을 적용합니다.

- 입력을 모노·24kHz로 변환한 뒤 녹음 전체에 하나의 피크 보정값을 적용합니다. 공식 학습/평가의 음량 정규화와 맞추되, 최대 증폭은 20dB이며 RMS가 `1e-5` 미만이면 무음으로 처리합니다. 약한 타격과 강한 타격의 상대 크기는 유지합니다.
- 기존 AI 타격을 삭제하거나 교체하지 않고, AI가 인식한 하이햇/심벌의 ±50ms 밖에 있는 경량 검출 하이햇 후보를 추가합니다. 정답 악보나 정해진 8비트 패턴을 사용하지 않습니다. 무음 판정 시 하이햇 보완도 실행하지 않습니다.
- 화면에 보완 개수를 표시합니다. 원본 MIDI는 **보완 전 모델 결과**이며, 검토 JSON의 `recovery.added_events`와 `score_events`에 각각 추가 타격과 보완 후 악보용 타격을 별도 보관합니다. 저장한 엔진 선택은 새로고침 후 복원됩니다.

검증 음원은 개발 5곡과 겹치지 않게 Beatles / Country1 / Disco / Grunge / LatinJazz를 미리 선택했습니다. 각 12초, 정답 타격 380개입니다. **이번 수정에 사용하지 않은 녹음이지, 모델의 학습 데이터와 독립임을 보증하는 자료는 아닙니다.** 검증 결과를 보고 임계값이나 곡별 예외를 추가하지 않았습니다.

| 드럼 단독 녹음 · micro onset F1 | 기존 ADT | 음량 보정 ADT | 보강 AI |
| --- | ---: | ---: | ---: |
| 개발 5곡 · 타격 313개 | 0.7133 | 0.7435 | 0.8018 |
| 추가 검증 5곡 · 타격 380개 | 0.8443 | 0.8486 | 0.8448 |

검증 세트에서는 누락이 60→37개로 줄었지만 오인식도 58→89개로 늘어, F1은 사실상 동일했습니다. Beatles/Disco/LatinJazz는 악화, Country1/Grunge는 개선됐습니다. **전반적 정확도 향상을 입증하지 못했으므로 선택형 실험 기능으로 유지합니다.** 오픈 하이햇/잔향/심벌을 닫힌 하이햇으로 잘못 보완할 수 있습니다. 원본 전체 믹스의 F1은 개발 0.3716→0.4316, 검증 0.3941→0.4133이지만 여전히 낮습니다. 이 수치 역시 SAM 분리/실제 배포곡/악보 레이아웃 정확도가 아닙니다.

반복 토큰 문제를 제한하는 `backend/adt_decoding.py`도 별도로 시험했습니다. 문법·시각 순서·동일 시각/종류 중복은 막지만 다른 오인식 타격을 고르는 문제가 남았습니다. 개발 세트에서 보강 후 F1이 0.7915로 일반 greedy의 0.8018보다 낮아 **보강 AI에도 적용하지 않았습니다.** 연구용 `AKBO_DRUM_DECODING=constrained`로만 실행할 수 있습니다. 실제 적용된 입력 gain, 디코더, 토큰 한도 도달/강제 변경은 검토 JSON에 남습니다.

재현(앞의 모델 환경 설정 필요):

```sh
.venv/bin/python scripts/prepare-drum-benchmark.py --accept-noncommercial --partition validation
# 기존 모델 기준선 (보완 변형은 hihat-fusion-experiment로 구분)
AKBO_DRUM_NORMALIZATION=none AKBO_DRUM_DECODING=greedy .venv/bin/python scripts/benchmark-drums.py --manifest .data/drum-benchmark/mdb-validation/manifest.json --output .data/validation-baseline --include-mix
# 앱의 보강 AI와 같은 구성: peak+greedy ADT 및 하이햇 보완을 각각 평가
```

개발 자료의 기존 경로는 유지하며 검증 자료는 `.data/drum-benchmark/mdb-validation`에 분리합니다. 선택·길이·리비전이 다른 기존 폴더는 덮어쓰지 않고, 중단된 다운로드는 동일 선택으로 재시도할 수 있습니다. 보고서는 데이터 출처/정답, 설정, 코드 SHA-256, 원시 모델 출력을 보존합니다. `hybrid` 시간은 AI·경량 검출·보완을 모두 포함하고, 정규화/디코더가 앱과 다르면 `hihat-fusion-experiment`로 구분합니다.

2차 검증: 서버 테스트 **309개**, 프런트엔드 **25개**, 별도 실제 ADT/보강 AI 추론·무음 테스트 **4개** 통과. 일반 CI는 GPU 1개와 실제 모델 4개를 건너뜁니다. 로컬 화면에서 보강 AI 선택→실제 12초 녹음 재채보→SVG 표시→새로고침 후 선택 유지→원본 MIDI/검토 JSON 다운로드(200)를 확인했습니다. 회사 서버나 Git 원격에는 반영하지 않았습니다.

### 정확성 우선 · 문맥 교차검증 · 3차 · 2026-10-06

`교차검증 AI · 3회 분석 (실험)`을 추가했습니다. 동일한 피크 보정 음원을 0 / 약 0.853 / 1.707초 패딩으로 분석해 2.56초 청크 경계를 달리합니다. 같은 드럼 종류·시각(최대 50ms 범위)이 **서로 다른 분석에서 2번 이상** 검출돼야 채택합니다. 동일 분석의 중복은 투표를 늘리지 않으며, 킥을 하이햇으로 강제 변경하거나 규칙적인 비트로 채우지 않습니다. 하이햇 추가 보완도 이 모드에는 적용하지 않습니다.

같은 모델의 문맥 변경이므로 독립 모델 3개의 확률적 신뢰도가 아닙니다. 일관된 오인식은 남고 약한 타격은 누락될 수 있습니다. 시작 0초의 실제 타격이 토큰/MIDI 반올림으로 음수가 되는 문제는 최대 11.2ms까지만 복원하며, 더 이른 패딩 구간 예측은 버립니다. 모든 보정·제외는 `runtime.timing_review`에 기록합니다.

| 드럼 단독 녹음 · micro onset F1 | 기존 ADT | 피크 보정 1회 | 피크 보정 3회 교차검증 |
| --- | ---: | ---: | ---: |
| 개발 5곡 · 정답 313타격 | 0.7133 | 0.7435 | **0.8331** |
| 추가 검증 5곡 · 정답 380타격 | 0.8443 | 0.8486 | **0.8929** |

검증 5곡에서 기존 대비 누락 **60→34개**, 추가 오류 **58→49개**, precision **0.8466→0.8759**, recall **0.8421→0.9105**입니다. 피크 보정 1회와 비교하면 10개 구간의 F1이 모두 올랐지만, 기존 무보정 경로와 비교하면 Beatles/Disco는 악화됐습니다. 그래서 자동/전용 AI 기본값은 그대로 두었습니다. 실제 노래 전체·회사 배포곡·SAM 분리 결과의 정확도 개선이나 학습 데이터와 독립인 평가를 뜻하지 않습니다. F1은 악기 종류+온셋 ±50ms 점수이지 “악보 89% 정확”이라는 뜻이 아닙니다.

개발+검증의 킥 추가 오류는 **20→7개**로 줄었고 실제 킥 검출은 합계 173개로 같았습니다(곡별 누락 보존을 뜻하지 않음). 검증 하이햇 추가 오류는 **31→8개**, 검출은 **140→168개**였습니다. 그러나 새 결과에도 Rock 약 0.28초, Country1 약 3.37초에서 하이햇 누락과 근처 추가 킥이 함께 있어 **하이햇→킥 혼동 해결이라고 할 수 없습니다.** 페달 하이햇 정답 1개는 모든 방식에서 누락됐습니다.

재현(기존 모델·자료 준비 후):

```sh
AKBO_DRUM_NORMALIZATION=peak AKBO_DRUM_DECODING=greedy AKBO_DRUM_CONTEXT_PASSES=3 .venv/bin/python scripts/benchmark-drums.py --manifest .data/drum-benchmark/mdb/manifest.json --output .data/context-development
AKBO_DRUM_NORMALIZATION=peak AKBO_DRUM_DECODING=greedy AKBO_DRUM_CONTEXT_PASSES=3 .venv/bin/python scripts/benchmark-drums.py --manifest .data/drum-benchmark/mdb-validation/manifest.json --output .data/context-validation
```

이 모드의 `drums.raw.mid`는 **교차검증 통과 후·박자 정렬 전** 결과입니다. 검토 JSON의 `runtime.consensus.pass_events`와 `candidates`에 3회 전체 후보·투표·보류 타격을 보관합니다. 화면에도 보류 개수와 합의가 정답 확률이 아니라는 설명이 나옵니다. 보강 AI는 환경변수와 무관하게 1회 분석으로 고정하고, 교차검증 모드는 피크 보정+greedy+3회로 고정합니다. `benchmark-drums.py`의 3회+하이햇 추가 조합은 `hihat-fusion-experiment`이며 앱의 보강 AI와 다릅니다.

평가기는 정답/추정에서 아직 매칭되지 않은 다른 종류의 근접 타격을 `possible_confusions` / `confusion_counts`로 따로 보고합니다. 올바르게 인식된 동시 킥을 다시 사용해 하이햇→킥 혼동으로 세지 않습니다. 모호한 후보를 표시하며, 이는 원인 확정이 아닌 검토용 추정입니다.

별도로 미리듣기의 페달 하이햇(GM44)이 낮은 사인파로 재생되던 오류와 사이드스틱(GM37)의 음수 주파수 계산을 수정했습니다. 11종의 음색을 명시적으로 정의합니다. **재생 오류 수정은 인식 모델의 킥/하이햇 혼동 해결과 별개**이며, 미리듣기는 여전히 간단한 합성음입니다.

### 전 악기 채보 근거 보관

실제 음원 채보 시 6개 악기 모두 `{instrument}.notes.json`을 저장하고 화면의 `채보 당시 음표 데이터 (수정 전)`에서 내려받을 수 있습니다. 악기 후처리 이후, 악보의 박자 격자·시작 오프셋 적용 이전 음표입니다. 입력 음원 SHA-256, 엔진/모델 출처와 초 단위 시작·종료/실음 MIDI/강도를 포함합니다. 강도는 신뢰도나 정답 확률이 아니고, 이후 수동 수정·악보 가져오기 내용도 반영하지 않습니다. 샘플은 알려진 작곡 데이터이므로 실제 추론 근거로 표시하지 않습니다.

음표 수·유한값·음원 범위·파일 크기를 검사하고, 추론과 악보 생성이 성공한 뒤 기존 파일을 교체합니다. 실패/취소 시 이전 결과를 보존하는 회귀 테스트를 추가했습니다. 이전 프로젝트에서 근거 파일이 없으면 링크를 표시하지 않으며 ZIP에도 넣지 않습니다. 모델 인식 오류와 박자 정렬/악보 표현 오류를 분리해 추적하기 위한 기반입니다.

### 실제 채보 비교 도구

샘플 화면은 원래 작곡 음표를 표시하므로 모델 평가가 아닙니다. 다음 명령은 달리, 여섯 자작 합성 WAV를 **실제 채보 엔진**에 넣고 기존 알고리즘과 비교합니다. `.data/` 결과는 Git에서 제외됩니다.

```sh
.venv/bin/python scripts/evaluate-transcription.py --demo-seconds 10 --compare-legacy --output .data/quality-check
# 더 복잡한 반복음·저음·스트럼·다성 화음·지속음: 실제 엔진, 합성 진단 전용
.venv/bin/python scripts/evaluate-transcription.py --synthetic-challenges --output .data/pitched-challenges
```

동일 연주의 정답 구간이 있다면 `--audio clip.wav --reference reference.json --instrument bass --output .data/reference-check`를 사용합니다. 정답 형식은 `{"bpm":120,"events":[[0.0,0.5,40,0.8]]}`로 시작초·종료초·실음 MIDI 음정·세기 순서입니다. 음원과 정답의 시작 위치를 맞춰야 하며 다른 편곡의 악보를 그대로 정답으로 사용하면 안 됩니다.

보고서의 F1은 **동일 음정 + 시작 시각 ±50ms**의 일대일 매칭 값입니다. 음 길이 정확도, 악보 레이아웃, 가사, 운지 점수가 아닙니다. 종료 시각 오차는 매칭된 음만 집계하며 드럼의 실제 타격 길이 품질 척도로 해석하지 않습니다. 2026-10-06의 10초 합성 비교에서 베이스 F1 0.4082→1.0000, 기타 0.9153→1.0000, 드럼 0.7865→0.9091이었습니다. **같은 드럼 테스트에서 스네어 9개는 전부 누락됐습니다.** 나머지 세 악기는 음정/온셋 F1이 모두 1.0000이었지만 보컬의 중앙 온셋 오차는 5.8ms→28.3ms로 늘었습니다. 이는 작은 합성 회귀 검사이며 실제 노래의 정확도나 전반적인 성능 향상 보증이 아닙니다.

추가한 `--synthetic-challenges`는 악기별 8초의 반복음·스트럼·다성/지속 화음을 사용합니다. 3차 실제 CPU 실행에서 보컬 F1 **1.0000**, 베이스 **0.9412**, 기타 **0.5882**, 피아노 **0.9091**, 신디 **0.6923**이었습니다. 기타의 옥타브 배음 추가, 피아노의 안쪽 화음 누락, 신디의 상단 음 누락·지속음 분절, 베이스의 끝부분 추가 음이 악보 생성 이전부터 관찰됐습니다. **다른 악기의 인식기를 이번 단계에서 개선했다는 수치가 아니라, 단순 데모가 숨기던 한계를 재현한 기준선**입니다. 분석 파형은 현실적인 악기 녹음이 아니며 이후 실제 연주로 검증해야 합니다. 음표 정답·파형 생성 규칙은 고정하고 코드/음원/정답 해시를 보고서에 남깁니다.

3차 검증: 서버 **435개**, 프런트엔드 **37개**, 별도 실제 ADT 1회/보강/교차검증·무음 **6개** 통과. 일반 테스트의 GPU 1개·실제 모델 6개는 명시 실행용으로 건너뜁니다. Orca 로컬 브라우저에서 12초 드럼 녹음의 교차검증 채보→SVG 표시→새로고침 후 선택 유지→음표/검토 JSON·MIDI 다운로드(200)를 확인했습니다. 회사 GPU 서버·Git 원격에는 반영하지 않았습니다.

### 다성 음표·지속음 검증 · 4차 · 2026-10-06

신디사이저에 선택형 `지속음 보강 (실험)`을 추가했습니다. **기본은 기존 채보이며, 전체 악기 함께 채보도 기존 방식입니다.** 신디 파트에서 방식을 선택하고 다시 채보하면 현재 악보를 대체합니다. Basic Pitch의 한 번 추론한 원시 온셋/음정 반응을 기존 규칙과 새 규칙으로 각각 해석합니다. 새 규칙은 시작점이 확인된 음만 만들고, 음별 초기 반응에 비례한 지속 기준으로 추적하며 실제 재타격에서 끊습니다. 서로 다른 음정을 독립적으로 추적하고, 옥타브가 겹친다는 이유로 삭제하지 않습니다. 천천히 시작하는 패드·약한 타격 누락과 잘못 추가되는 음표는 여전히 가능합니다.

`synthesizer.transcription.json`은 기존/보강 음표 전체, 음별 onset/frame 반응, 종료 근거, 옥타브 겹침 후보, 입력 음원 SHA-256을 보관합니다. 반응값은 정답 확률이 아니고, 겹침 후보도 오류 확정이 아닙니다. 이후 수동 수정은 포함하지 않습니다. 실제 옥타브 연주도 함께 지우던 배음 삭제 규칙은 채택하지 않았습니다. 재채보 실패 시 이전 악보·근거를 보존하며, 이전 악보가 남아 있어도 실패 안내를 표시합니다.

실제 CPU 엔진으로 개발 합성음 5개와 **후보를 고정한 뒤 처음 평가한 별도 합성 검증음 10개**를 비교했습니다. 검증 파형은 풍부한 배음, 조옮김/미세 디튜닝, 실제 옥타브 화음, 높은 반복음, 진폭이 변하는 지속음 및 보컬·베이스 대조군을 포함합니다. 두 세트 모두 현실적인 악기 녹음·SAM 분리 결과가 아니며 실제 노래의 정확도로 해석하면 안 됩니다. 참조 종료 시각은 합성 엔벨로프의 정의입니다.

| --- | --- | --- | --- |
| 기타 · 26 | 0.7586 → 0.6471 | 0.6897 → 0.5882 | 악화, 적용 보류 |
| 피아노 · 32 | 0.9412 → 0.8101 | 0.8529 → 0.7342 | 악화, 적용 보류 |

기타·피아노는 개발 자료의 음정/온셋 F1이 올라도 별도 검증에서는 가짜 음표가 늘었습니다. 피아노는 개발 자료에서 누락된 음을 복구하면서 쉼표를 넘어 길게 늘이는 문제도 있었습니다. **낮은 수준의 디코더/비교 도구에는 연구 목적으로 세 악기를 남기지만, 공개 채보 API는 신디 외 `adaptive` 요청을 작업 시작 전에 거절합니다.** 검증 결과를 보고 임계값을 재조정하지 않았습니다. 향후 변경에는 새로운 독립 검증 자료가 필요합니다.

Orca 로컬 브라우저의 자작 합성음 작업실에서 신디 모드 선택→실제 CPU 재채보→대보표 SVG 표시, 새로고침 후 신디 재선택 시 방식 복원, 음표/검토 JSON·MIDI·MusicXML 응답 200, 기타/피아노 보강 선택 비노출을 확인했습니다. SAM 분리는 이 검증에 포함되지 않습니다. 회사 GPU 서버·Git 원격에는 반영하지 않았습니다.

### MulTTiPop 실제 곡 평가 연결 · 2026-10-06

[MulTTiPop](https://gclef-cmu.org/multtipop/)의 **개발 분할 MIDI·메타데이터만** 고정 리비전 `341cd7f31d29d092862fe7bdd49f9ccdce7825b0`에서 준비하는 도구를 추가했습니다. 모델·음원 다운로드나 학습 기능은 아닙니다. 기본 24개 구간은 아티스트·장르 다양성을 기준으로 결정하며, 채보 결과나 MIDI 품질을 보고 쉬운 곡으로 바꾸지 않습니다. 준비에 실패한 사례도 목록에 남깁니다. `test` 자료는 요청하지 않습니다.

```sh
# 네트워크 사용: 공개 MIDI/메타데이터만, 새 폴더 필요
.venv/bin/python scripts/prepare-multtipop.py --count 24 --output .data/multtipop-dev
# 오프라인 검수 상태 확인: 새 보고서 파일 필요
.venv/bin/python scripts/benchmark-multtipop.py \
  --manifest .data/multtipop-dev/manifest.json --output .data/multtipop-audit.json
```

`manifest.json`의 `references_prepared`는 **정답 후보 다운로드 완료**이지 `benchmark_ready`가 아닙니다. MIDI 체크섬·실제 템포 지도·드럼 채널·모든 파트·음표 범위를 검사합니다. 정렬된 MIDI는 이미 구간 시작 기준 초 단위이므로 원곡 BPM으로 다시 늘이거나 YouTube 시작 시간을 또 빼지 않습니다. 드럼은 원래 MIDI 번호를 보존하며, 채보 모델 전용 번호 변환이나 표시용 킷 축약을 적용하지 않습니다.

실제 채점 전에 다음 검수가 필요합니다.

1. 각 곡 폴더의 `audit.json`을 참고해 `mapping.json`의 **모든 파트**에 `instrument`, 검토 `reason`을 지정합니다. 선택지는 여섯 악기 또는 `ignore`이며 무시 사유도 기록합니다. 보컬은 `role: "lead"` 또는 `"backing"`이 필요합니다. GM 프로그램/트랙명은 참고 정보일 뿐, 자동 확정하지 않습니다. 검수 후 `reviewed: true`, `reviewer`를 작성합니다.
2. 사용 권한이 있는 **동일 녹음·동일 구간**의 로컬 오디오를 준비해 manifest의 `audio`, `audio_sha256`, `audio_rights_confirmed`, `audio_alignment_reviewed`를 채웁니다. 전체 곡이 아닌 지정 구간이 필요하며, 길이·해시·유한 샘플도 확인합니다. SHA-256은 macOS에서 `shasum -a 256 <파일>`로 확인할 수 있습니다. 제공 MIDI의 라이선스가 원곡 음원 이용권을 대신하지 않습니다.
3. 그 음원을 기존 SAM 경로로 처리하고, 여섯 분리 WAV와 여섯 `*.notes.json`을 내보냅니다. 수동 악보 수정본·격자 정렬 이후 음표는 이 평가에 사용하지 않습니다. 스템이 무음이어도 해당 악기의 명시적인 빈 음표 파일이 필요합니다.
4. 아래 형식의 예측 manifest를 작성해 `--predictions`로 전달합니다. `cases`는 처음 선정한 전체 ID를 빠짐없이 포함해야 하고, `instruments`에는 예시의 보컬 외 베이스·드럼·신디·기타·피아노도 같은 구조로 추가합니다. 음표/스템 경로는 예측 manifest 폴더 안의 상대 경로여야 합니다. `separation_reviewed`는 실제 처리 출처 확인 후에만 설정합니다.

```json
{
  "schema": "akbo.multtipop.predictions", "schema_version": 1,
  "cases": [{
    "id": "선정된_ID", "mix_sha256": "검수한_원본_음원_SHA256",
    "pipeline": "sam-separated-stems", "separation_reviewed": true,
    "separation_provenance": {"engine": "sam-audio", "model": "실제 사용한 모델·리비전"},
    "instruments": {"vocal": {"notes": "선정된_ID/vocal.notes.json", "audio": "선정된_ID/vocal.wav"}}
  }]
}
```

```sh
.venv/bin/python scripts/benchmark-multtipop.py \
  --manifest .data/multtipop-dev/manifest.json \
  --predictions .data/multtipop-predictions/manifest.json \
  --output .data/multtipop-evaluation.json
```

평가는 악기별 음정+시작점 ±50ms의 P/R/F1, 누락/추가 음표, 드럼 타격의 가능한 혼동, 건반·기타·베이스·보컬의 종료 길이 진단을 분리합니다. 빈 정답 파트의 잘못 추가된 음표도 제외하지 않습니다. 드럼 `35→36` 같은 번호 차이도 원시 GM 기준에서는 오답이므로, 표시용 악보에서 같은 킥으로 그려진다고 이 점수가 같아지지는 않습니다. 보컬은 지정된 리드·코러스를 모두 합산하고, 무시한 파트가 있으면 전체 편곡 평가가 아님을 표시합니다. 참조 없는 파트의 F1 0은 별도의 `reference_present` 값과 함께 읽어야 합니다.

한 사례라도 검수/출처/입력이 누락되면 전체 합산 점수를 내지 않습니다. 검수 전 상태를 0점이나 성공으로 포장하지 않으며, JSON/WAV 크기·경로·비유한 값·출처 해시를 검사합니다. SAM 실행 출처는 사용자가 기록한 정보이며 파일 해시만으로 실제 실행 과정을 독립적으로 증명하는 것은 아닙니다. 데이터 원본 출처도 고정 URL에서 받은 준비 기록을 함께 보존해야 합니다. 이 개발 세트 결과는 독립 검증 성능, 악보 가독성, 운지, 가사 정확도 또는 분리 SDR을 뜻하지 않습니다. MIDI 자체의 편곡 차이와 라벨 오류도 청취 검수해야 합니다.

[Sound Demixing Challenge 2023](https://www.aicrowd.com/challenges/sound-demixing-challenge-2023)은 조사만 했습니다. 음악 트랙은 보컬·베이스·드럼·`other` 4개 음원의 **분리** 과제이고, `other`에는 기타·피아노·신디 등이 포함됩니다. SDR은 파형 분리 지표이므로 채보 정확도를 보장하지 않습니다. 이번 작업에서 해당 모델·데이터·분리 엔진은 도입하지 않았으며 기존 SAM 경로와 앱 기본 인식 설정도 바꾸지 않았습니다.

최종 검증: 실제 pYIN 검사를 포함한 서버 **1,266개 통과·8개 별도 실행 제외**, 별도 ADT CPU 실행 **6개 통과**, 프런트 **92개 통과**, TypeScript/Vite 빌드 통과. 선택형 torch 디코더의 가짜 로짓 검사에서는 예산 끝에서 잘못된 토큰 때문에 강제 EOS가 발생하는 경우와 자연 EOS를 구분했습니다. 마지막 v2 실제 CPU 실행 2건도 통과했습니다: 사용자 곡은 119회 강제 수정 후보를 거부하고 기존 82개 원시 이벤트를 그대로 유지했으며, Reggae는 1회 수정 후보를 수락한 36개 이벤트가 제한 정책 재구성과 정확히 일치했습니다. 실행 근거는 `.data/drum-retry-20261006/final-v2/report.json`입니다. 이 테스트 숫자나 형식 복구 자체는 채보 정확도 수치가 아닙니다.

### 원본 독립 분리·박자 진단·독립 모델 실제 비교 · 2026-10-07

**사이트에 연결한 기능과 연구용 모델을 구분합니다.** 새 업로드의 분리 방식 선택과 박자 검토 근거는 웹/API에 연결했습니다. 아래 STRUM·CREPE·YourMT3+는 실제 CPU 추론과 비교까지 구현한 **별도 CLI 연구 경로**이며, 웹의 채보 엔진 목록이나 자동 보정에 연결하지 않았습니다. 기존 모델을 일괄 교체할 정확도 근거가 없기 때문입니다.

#### 사이트: 원본에서 각 악기 독립 추출

새 업로드에서 `separation_strategy=independent`를 선택하면 보컬·베이스·드럼·신디·기타·피아노 모두 동일한 준비된 원본의 복사본을 SAM에 전달합니다. 앞 악기를 뺀 잔여 신호를 다음 악기에 쓰는 기존 `sequential`은 기본값으로 유지합니다. 목표는 앞 단계의 과도한 제거가 뒤 악기로 전파되는 영향을 비교하는 것입니다. **독립 추출의 실제 분리 품질 개선은 아직 검증하지 않았습니다.**

독립 결과끼리는 같은 소리가 겹칠 수 있어 합산 보존·잔여 음원을 제공하지 않습니다. 화면과 ZIP 안내에도 이를 명시하며, 믹서는 원본으로 시작하고 분리 결과는 한 악기씩 비교 청취합니다. 분석 전용 업로드와 독립 분리의 잘못된 조합, 추론 중 입력 변조·잘못된 길이·비유한 값, 취소와 중간 실패를 검사합니다. 모의 SAM/API 테스트는 여섯 번의 원본 입력과 중간 실패 시 완료 파일 보존·GPU 정리를 확인했으며 **실제 GPU 재추론은 수행하지 않았습니다.** 기존 프로젝트의 재분리·악보 교체도 자동 실행하지 않습니다.

#### 사이트: 일정 BPM의 적합성과 템포 모호성

`BPM · 박 위치 분석`에 전체 박열의 일정 격자 적합, 반속/배속 후보, 구간별 주기 변화, 기존 분석 추천 BPM의 누적 밀림 근거를 추가했습니다. 일정한 박열이 충분히 확인될 때만 별도 정수 BPM 비교 버튼을 제공합니다. 박 간격이 불규칙하거나 구간이 짧으면 후보를 거절하며, **BPM·마디 첫 박·기존 악보는 자동 변경하지 않습니다.** 주기성·격자 잔차는 정확도나 정답 다운비트가 아닙니다. 변속 템포 지도·셋잇단음표의 악보 반영은 아직 별도 과제입니다.

고정 100/137 BPM 합성 클릭에서 정밀 후보를 확인했고, 90→120 BPM 변화에서는 일정 BPM을 강제하지 않도록 검사했습니다. 사용자 곡의 원본/분리 드럼 앞 180초는 종전 추천 99 BPM을 유지했습니다. 박열 적합은 약 100 BPM이지만 95백분위 잔차가 각각 약 .104/.096초로 커서 **정밀 후보를 거절**했습니다. 이 결과로 기존 악보의 미검수 120 BPM을 100으로 바꾸지 않았습니다. 기록: `.data/rhythm-research-20261006/final-v1/report.json`.

2. 구간별 주기 변화 진단은 구현했지만 템포 지도/다운비트·정밀 음표 길이·쉼표 정리의 자동 악보 반영은 남았습니다. 16분음표 격자로 표현하지 못하는 셋잇단음표·못갖춘마디·독립 성부를 함께 확장합니다.
3. 사용자 보유/이용 가능한 MusicXML을 우선 기준 악보로 받아 스타일 재조판 → 오디오 정렬 → 차이 검토. PDF OMR·출처/이용 조건을 확인한 악보 검색은 별도 단계이며 아직 자동화하지 않음.

자작 합성 음원 4초를 실제 SAM으로 여섯 단계 분리하고 길이·유한 값·WAV 저장·합산 보존을 확인합니다. 이는 실행 연결 검증이며 실제 곡의 악기별 분리 정확도/채보 품질 검증을 대체하지 않습니다.

TAB/가사 테스트는 줄·프렛·튜닝 검증, 한 줄 동시 발음 거절, 화음 운지 배정, 미배정 음정 보존, 두 보표의 마디 길이, 쉼표 위치 가사, MusicXML 요소 순서, LRC 시간/오프셋/충돌, 파트 간 가사 복사와 수정본 보호를 확인합니다.

가져오기 테스트는 실제 생성 XML의 음정·타이·운지·가사 왕복, 네임스페이스/MXL, 미지원 표기·부정확한 시간 거절, 크기/숫자/엔티티/압축 경로 제한, 음원 없는 프로젝트와 원본 XML/ZIP 보관, 비파괴 미리보기·revision·최초 생성본 보호를 확인합니다. TAB 순서·카포/실제 음정·기본 연주 표시·수동 줄/페이지 시작과 일괄 편집 충돌도 테스트합니다.

박자 테스트는 여섯 박자의 드럼/TAB 성부별 정확한 마디 길이, 6/8의 3+3 빔, 변박을 가로지르는 타이·가사 왕복, MIDI 박자 변경 시각·전체 길이, 점음표 템포 환산, 잘못된 박자·불완전한 마디·600마디 초과 거절, 기존 JSON/클라이언트 호환, 빈 악보·재채보 API를 검증합니다. 프런트엔드에서는 재배치의 비파괴성·마디 경계 강조·가사/재생 시간 유지·메모 합치기·입력 제한을 확인합니다. 브라우저에서는 자작 샘플의 6/8 드럼·변박·가사·원본 재생 강조와 모바일 3/4 TAB의 12칸/가로 넘침을 확인했습니다. 네이티브 모바일 스크린샷은 웹뷰 합성기 제한으로 빈 이미지가 나와 DOM 배치 측정과 실제 악보 SVG 렌더로 확인했습니다.

CPU 분석 테스트는 실제 클릭 음원 BPM 추정/무음 거절, 분석 전용 업로드의 SAM 미호출, 빈 TAB 악보 생성, 가사 검토와 실패 시 이전 초안 보존, 전체 여섯 파트 적용의 음표/운지/최초 생성본 보존, revision 충돌, 잘못된 시간 입력, 오프셋 채보, 1박/2박 빔과 16분음표의 두 번째 빔을 확인합니다. 프런트엔드 테스트는 미리듣기 범위의 음표 경계·속도·원본 재생 시점·LRC 오프셋을 확인합니다. 로컬에서는 직접 작성한 합성 발화로 실제 Whisper base CPU INT8의 단어/타임스탬프 출력도 확인했습니다. 이는 **실제 노래의 가사 정확도 검증이 아닙니다.** 모델 다운로드·추론은 일반 CI 테스트에서 실행하지 않습니다.

전 악기 개선 테스트는 대보표/교차 손 배정/빈 아래 보표의 왕복, 기존 저장본·옛 클라이언트 호환, 보표 전환 시 MIDI 불변, 여섯 파트의 가사 위치, 실제 pYIN 합성음 추론, 악기별 모델 파라미터, 드럼 동시 타격·종료 오검출·8/16비트 기보, 별도 드럼 워커의 성공/오류 계약을 확인합니다. 로컬 브라우저의 실제 SVG로 여섯 파트의 가사, TAB 우선, 대보표↔단일 보표, 수동 손 변경과 드럼 연결선을 확인했습니다. 무음 보표의 첫 박 가사가 마디 중앙으로 보이지 않도록 온쉼표 대신 시간 위치가 있는 쉼표에 배치합니다. 회사 배포 서버와 기존 프로젝트는 변경하지 않았습니다.

## 합의한 여섯 개발 과제 · 진행 중

여섯 항목 전체가 개발 범위입니다. 아래는 완료 선언이 아니라 현재 단계와 남은 작업입니다. 승인된 SAM Audio base와 RTX 3090에서 합성 음원의 실제 CUDA 추론 연결은 확인했으며, 실제 곡의 분리·채보 품질 검증은 남아 있습니다.

1. TAB: 기본 순서·튜닝/카포·자동 운지·뮤트/단순 벤딩·일괄 수정 구현. 다음은 슬라이드·해머링/풀링·프리벤드/릴리스·운지 표시 QA.
2. 기존 악보: 제한된 MusicXML/XML/MXL 및 건반 두 보표 가져오기 구현. 다음은 보이스·조표/이명동음·현재 미지원 표기의 보존 범위 확대. PDF/이미지 OMR은 별도 후속 기능.
3. 완성형 기보: 기본 연주 표시·박자 선택(2/4·3/4·4/4·6/8·9/8·12/8)·마디별 변박·점음표 입력 구현. 다음은 잇단음표 시간 모델, 못갖춘마디, 반복/괄호, 다이내믹·코드, 오선 직접 입력.
4. 합주 재생: 합성음 마디 범위·속도/반복·원본/분리 음원 마디 강조 구현. 다음은 음표 커서·템포 지도 기반 정밀 동기화·사운드폰트.
5. 채보 품질: 악기별 경로·건반 대보표·CPU 합성 비교·실제 ADT 추론/수동 정답 비교·엔진/입력 선택·원시 타격 보존 구현. 실제 SAM CUDA 통합 스모크 테스트는 기존 통과. 다음은 실제 곡 기준 분리 품질·드럼 음색별 실패 개선·가사 시간·손/독립 성부·운지 검증.
6. 가독성/출력: A4·스타일·2/4마디·드럼 빔·수동 줄/페이지 시작 구현. 다음은 복잡한 실제 곡의 가사/주법 겹침 QA·마디 폭·가사 여백 세부 조절.

공개 서비스의 인증·사용자별 저장소·작업 큐/재시도·보관 정책·배포/모니터링은 별도 운영 확장입니다.

## 서버 배치

재빌드 시 기존 `dist/assets/` 파일을 보존해 이미 열린 탭이 이전 버전의 악보 렌더러를 계속 불러올 수 있게 합니다. HTML은 `Cache-Control: no-cache`로 재검증합니다. 이전 배포에서 이미 삭제된 파일을 요청하는 탭은 편집 내용을 보관한 뒤 새로고침해야 합니다. 과거 자산을 정리할 때는 기존 탭의 작업이 종료된 유지보수 시점에 수행하세요.

```sh
./start.sh --host 127.0.0.1 --port 8000
```

빌드한 `dist/`가 있으면 API가 프런트엔드도 같은 출처로 제공합니다. 기본 개발 서버는 로컬에만 바인딩합니다. 이 버전은 개인 작업실용이며 계정 인증·사용자별 권한 분리를 포함하지 않습니다. 공개 서비스로 운영하려면 인증, 사용자별 저장소, 요청 제한, 보관 정책, HTTPS 프록시, GPU 작업 큐를 추가해야 합니다. `uvicorn --workers 1`로 실행해야 단일 모델·작업 큐·파일 저장소가 일관되게 동작합니다.

작업과 파일은 `.data/<job-id>/`에 보관되고 프로젝트 목록은 브라우저 localStorage에 저장됩니다. 원본과 결과 파일은 자동으로 삭제하지 않습니다. 서버 재시작 때 미완료 작업은 중단 상태로 바뀌며 완료된 파일은 보존됩니다. ZIP은 디스크에 생성한 뒤 스트리밍합니다. 대용량 오디오가 다수 쌓이는 공개 서비스에는 디스크 용량 관리와 보관 정책이 추가로 필요합니다.
